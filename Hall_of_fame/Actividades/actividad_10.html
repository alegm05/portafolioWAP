Actividad 10: Lab: File path traversal, traversal sequences stripped with superfluous URL-decode

Laboratorio de evaluación ofensiva enfocado en la evasión de filtros (WAF Bypass) mediante Double URL Encoding, explotando la desincronización entre la validación de entrada y la decodificación superflua en el backend.

NIVEL / TIPO

Dificultad: Practitioner
Vulnerabilidad: CWE-22 (Improper Limitation of a Pathname to a Restricted Directory)

OBJETIVO TÉCNICO

La aplicación bloquea entradas que contienen saltos de directorio (../), pero ejecuta una decodificación URL superflua posterior. El objetivo es enviar un payload doblemente codificado para burlar el filtro inicial y extraer /etc/passwd.

[THEORY_02]

Marco Teórico

Fundamentación de la Vulnerabilidad

Clasificada bajo el estándar OWASP (A01:2021 - Broken Access Control), esta falla se magnifica por un error lógico de "validación pre-decodificación". La validación de seguridad siempre debe realizarse sobre los datos en su formato final decodificado.

Mecánica del Double URL Encoding

Consiste en codificar el carácter % resultante de una primera codificación URL. Por ejemplo, el texto ../ se convierte primero en %2e%2e%2f. Al aplicar una segunda capa, el % se vuelve %25, resultando en %252e%252e%252f.

¿Por qué burla los filtros? (Desincronización WAF-Backend)

El filtro perimetral recibe el payload doblemente codificado y lo decodifica una sola vez, viendo %2e%2e%2f. Como esto no coincide con ../, lo deja pasar. Posteriormente, el backend, debido a un error de diseño, aplica una decodificación secundaria "superflua", restaurando el ataque original antes de interactuar con el sistema de archivos.

[EXEC_03]

Procedimiento

Fase 1: Identificación del Filtro

Tras interceptar el tráfico en Burp Suite, se aisló la solicitud GET /image?filename=40.jpg en el módulo Repeater. Al inyectar el payload en texto claro (../../../etc/passwd), el servidor respondió con un HTTP/2 400 Bad Request, confirmando que existe un mecanismo defensivo bloqueando el Path Traversal estándar.

>_ Evidencia: Demostración del filtro activo bloqueando el payload estándar en texto claro y devolviendo un error de sintaxis.

Fase 2: Construcción del Payload (Double Encoding)

Para evadir el filtro, se utilizó la herramienta nativa de conversión de Burp Suite. Seleccionando la cadena maliciosa, se aplicó Convert selection > URL > URL-encode all characters en dos iteraciones consecutivas, transformando el texto en una cadena hexadecimal anidada.

>_ Evidencia: Aplicación de la segunda iteración de codificación (Double Encoding) sobre el texto ya cifrado usando el menú contextual.

Fase 3: Evasión (Bypass) y Exfiltración

Se inyectó el payload doblemente codificado (%2532%65...). El filtro de entrada lo permitió al no reconocer la firma, y la función superflua del backend lo decodificó restaurando la amenaza. El servidor procesó la ruta y devolvió un HTTP/2 200 OK con el volcado completo de cuentas de usuario.

>_ Evidencia: Ataque exitoso en Repeater mostrando el payload doblemente codificado a la izquierda y el volcado de /etc/passwd a la derecha.

Fase 4: Verificación de Compromiso

El éxito del ataque corrobora la desincronización del procesamiento. La plataforma de PortSwigger registra la extracción correcta del archivo crítico.

>_ Evidencia: Confirmación visual del estado "Lab Solved" validando la evasión del filtro y la resolución del reto.

[PAYLOAD_04]

Análisis Téc.

Mecánica del Payload de Evasión

HTTP Request - Double URL Encoding
GET /image?filename=%2532%65%2532%65%2532%66%2532%65%2532%65...etc%2fpasswd HTTP/2
Host: 0a61004e04fdfa...web-security-academy.net
Accept: image/webp, image/apng, image/*
Sec-Fetch-Site: same-origin
  • Evasión del WAF: El filtro lee la cadena decodificándola una vez (obteniendo %2e%2e%2f). Al no ver el patrón ../ bloqueado, permite el paso.
  • El Error de Backend: El backend de la aplicación, por una mala práctica de programación, somete esta entrada a un URL-decode secundario, transformando %2e%2e%2f nuevamente en ../ y materializando la exfiltración.

Defensa en Profundidad y Remediación

1. Regla de Oro: Decode First, Validate Later

El ciclo de vida correcto para procesar entradas exige aplicar todas las decodificaciones necesarias (URL, base64) hasta llegar al texto plano absoluto antes de ejecutar cualquier filtro de seguridad, sanitización o lista blanca.

2. Eliminación de Funciones Superfluas

Los servidores web y balanceadores modernos ya realizan automáticamente la primera decodificación URL de los parámetros antes de entregarlos al código base. Añadir llamadas manuales a funciones como urldecode() o URLDecoder.decode() en la lógica del negocio suele ser redundante y es la causa directa de este tipo de vulnerabilidades.

3. Abstracción Segura (Canonicalización)

Para mitigar definitivamente el Path Traversal no se debe confiar en el filtrado de cadenas. Se debe abstraer el sistema de ficheros de la entrada del usuario usando identificadores seguros en bases de datos o, en su defecto, resolver la ruta absoluta con getCanonicalPath() y verificar el directorio origen autorizado.
